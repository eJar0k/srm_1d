# Plugin-provided igniter — DESIGN

**Decision (user, 2026-10-05):** fix the stale-igniter problem in the
openMotor fork, refresh existing motor files, and have the fork take its
igniter definitions from srm_1d — *plugins control their preferred ignition
method*. Background: `docs/solver_verification/worklog/T1.md` (step 6–7).

## Problem

`bfc2f3f` corrected BPNV in srm_1d's library (M 0.030→0.0482, γ 1.25→1.17,
T_flame 2800→2719, new `gas_mass_fraction` 0.781; ≈2.12× less igniter gas).
The fork never learned it:

- `motorlib/igniter.py` hardcodes a 16-field `Pyrogen` schema (no
  `gas_mass_fraction`, no `Cp_gas`) and a 9-field `Igniter` chamber schema.
  `PropertyCollection.setProperties` drops unknown keys and
  `FloatProperty.setValue` silently ignores out-of-range values and raises on
  `None` — so a GUI round-trip is lossy by construction.
- Seeds hardcode the old BPNV: `uilib/defaults.py` `DEFAULT_PYROGENS`,
  `uilib/fileIO.py` `DEFAULT_IGNITER` (seeded by the 0.6.1→0.7.0 migration).
- The user's `%LOCALAPPDATA%\openMotor\openMotor\pyrogens.yaml` and every
  committed `motors/*.ric` embed the old BPNV. GUI runs therefore
  over-produce igniter gas (Chunc startup peak 12.654 vs 11.473 MPa).

## Decisions

**D1 — The plugin owns the igniter model.** srm_1d is the single source of
truth: the `Pyrogen` dataclass (fields + defaults), `_IGNITER_SIZING_DEFAULTS`
(chamber fields), the material library (`srm_1d/pyrogens/*.yaml`), and the
GUI metadata (labels / units / ranges / enum choices). The fork hardcodes none
of it.

**D2 — Generic fork contract.** `motorlib.solvers.SolverPlugin` gains five
optional igniter hooks (base-class defaults = "no igniter"):

| hook | returns |
|---|---|
| `get_igniter_material_schema()` | a fresh `PropertyCollection` for one material, or `None` |
| `get_igniter_chamber_schema()` | a fresh `PropertyCollection` for the chamber sizing, or `None` |
| `get_igniter_materials()` | `list[dict]` — the plugin's built-in material library |
| `get_default_igniter()` | `dict` — a default `data.igniter` block, or `None` |
| `upgrade_igniter_block(block)` | `(block, changed: bool)` — see D5; default passthrough |

plus `motorlib.solvers.get_igniter_provider()` → the first registered solver
whose `capabilities.get('igniter')` is truthy, else `None`. Nothing in the
contract is srm_1d-specific, so it can go upstream as a generic hook.

**D3 — Lossless storage.** `Motor` keeps the block as a raw dict,
`motor.igniterData` (deep-copied in and out), replacing the
`motor.igniter` / `motor.igniterPyrogen` PropertyCollections. `getDict` /
`applyDict` pass it through untouched except for the D5 upgrade. With no
provider the block still round-trips verbatim (the GUI igniter row is
already hidden for solvers without `capabilities['igniter']`).

**D4 — GUI editing writes back only what the user changed.** Editors build
the provider's schema collection from the raw dict (skipping `None`-valued
keys), snapshot `getProperties()` right after loading, and on save merge
ONLY the keys whose value differs from the snapshot into the raw dict.
Untouched keys — including `None` and out-of-range values — are never
rewritten. Picking a library material deep-copies the library dict into
`igniterData['pyrogen']` (no collection round-trip).

**D5 — Exact-match upgrade of superseded library snapshots (plugin-owned
history).** srm_1d keeps `SUPERSEDED_PYROGENS` (material name → list of exact
legacy material dicts) — initially one entry: the pre-`bfc2f3f` BPNV, i.e. the
`pyrogen` dict of the fork's current `DEFAULT_IGNITER`. `upgrade_igniter_block`
replaces the block's material with the CURRENT library entry only when it
matches a superseded snapshot exactly (every legacy key equal, floats rel tol
1e-9; any extra key must be absent or `None`). Chamber sizing is never
touched; customised materials never match, so user edits are safe; the call
is idempotent. Applied in: fork `Motor.applyDict`, fork `PyrogenManager`
library load, and srm_1d `load_igniter` (CLI parity — emits
`IgniterMaterialUpgradedWarning`). Future library corrections append the
outgoing version to `SUPERSEDED_PYROGENS`. No `.ric` format version bump.

**D6 — Library stays user-editable (mirrors openMotor's propellant
library).** `pyrogens.yaml` seeds from `get_igniter_materials()` when
missing; on load each entry is upgraded via D5 and any provider material
whose name is absent is appended; saved if anything changed. Materials are
held as raw dicts. `app.py` must discover plugins BEFORE constructing
`PyrogenManager` (today it is the reverse).

**D7 — Refresh existing files through openMotor itself.** A srm_1d tool loads
each `.ric` with the fork's `fileIO.loadFile` (+ migrations) → `Motor` →
`fileIO.saveFile` — i.e. the files are regenerated by openMotor code (the
`.ric` ownership rule), and D5 performs the upgrade. Every refreshed file is
diffed: the only permitted semantic change is the igniter material; any other
lost or altered data is a STOP.

## Out of scope

Upstream PR preparation; MTV / thermite CEA values (held); changing any
default igniter material or sizing; pushing anything.
