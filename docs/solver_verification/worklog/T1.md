## Step 7 — openMotor fork investigation (read-only; fork not edited)

Fork: `.../openMotor/openMotor` (branch `staging`, HEAD `92e425f`).

**Where the GUI gets/creates the igniter material — it is NOT srm_1d's library:**

* `motorlib/igniter.py` — openMotor's own `Pyrogen(PropertyCollection)` with a
  hard-coded 16-property schema: `name, a, n, rho, T_flame, M, gamma, impetus_W,
  heat_flux_cal_cm2_s, kappa_jet, form, particle_diameter_m, particle_LD_ratio,
  heat_delivery_mode, pellet_emissivity, radiation_absorption_length_m`.
  **No `gas_mass_fraction` and no `Cp_gas`.** `PropertyCollection.setProperties`
  silently drops unknown keys and `getProperties` emits only declared ones, so
  these two fields cannot survive a load/save through the GUI.
* `motorlib/motor.py` `getDict`/`applyDict` — `data.igniter` = chamber sizing
  (`Igniter` props) + nested `pyrogen` = `igniterPyrogen.getProperties()` (the
  16-key schema above).
* `uilib/pyrogenManager.py` — the GUI's reusable pyrogen library, persisted by
  `loadFile/saveFile(..., fileTypes.IGNITERS)` at
  `platformdirs.user_data_dir('openMotor','openMotor')/pyrogens.yaml`
  (`%LOCALAPPDATA%\openMotor\openMotor\pyrogens.yaml` on this machine). On first
  run (no file) it seeds `DEFAULT_PYROGENS` from `uilib/defaults.py`.
* `uilib/defaults.py` `DEFAULT_PYROGENS` and `uilib/fileIO.py`
  `DEFAULT_IGNITER` (seeded into pre-0.7.0 motors by `migrateMotor_0_6_1_to_0_7_0`)
  — both hard-code the **pre-`bfc2f3f` BPNV** (`M 0.030, gamma 1.25,
  T_flame 2800`, no `gas_mass_fraction`).
* `uilib/widgets/mainWindow.py` `applyMotorConfig` — picking a library pyrogen in
  the motor config row copies `libPyro.getProperties()` into
  `cm.igniterPyrogen` (the 16-key dict) — an embedded copy, mirrors the
  propellant picker. `motorEditor.py` supplies the picker names from
  `pyrogenManager.getNames()`.
* No import of srm_1d for materials anywhere in the fork (srm_1d is only
  imported by `motorlib/solvers.py` to register the solver plugin). `srm1d_plugin.simulate_motor`
  does `motor.getDict()` -> `load_igniter(motor_dict)`, i.e. it consumes exactly
  the 16-key GUI block.

**Evidence on this machine (read-only):** the user's live GUI library
`%LOCALAPPDATA%\openMotor\openMotor\pyrogens.yaml` (mtime Jun 4) holds a
single BPNV entry with `M 0.03, T_flame 2800.0, gamma 1.25` and no
`gas_mass_fraction`; the GUI-saved `motors/L1843mod.ric` in the main checkout
(untracked, 2026-08-15) has the same 16-key block with those values.

**Answer: NO.** After this T1 fix a newly GUI-created (or re-saved) motor will
still embed the stale material and will NOT carry `gas_mass_fraction`:

1. the GUI's pyrogen library file and its two code-level seed dicts hold the
   old BPNV values, and
2. even a library entry that had the right values could not carry
   `gas_mass_fraction` (nor `Cp_gas`) because openMotor's `Pyrogen` schema lacks
   them; and opening+re-saving a motor whose block contains the key would DROP
   it (by code reading of `applyDict`/`getDict`; not exercised in the GUI).

What T1 changes for the GUI path is *detection*: `simulate_motor` ->
`load_igniter` now emits `StaleIgniterMaterialWarning` listing the four
(or, for a re-saved block, the differing) fields. (Python prints the warning to
stderr; whether the GUI surfaces it is not verified.) Fixing the GUI side is a
fork change (add `gas_mass_fraction`/`Cp_gas` to `motorlib/igniter.py`, refresh
`DEFAULT_PYROGENS`/`DEFAULT_IGNITER`, migrate the user's `pyrogens.yaml`) or a
plugin-side overlay of library values by name — a decision reserved for the
user (DESIGN §5); not done here.

## Deviations from the spec / observations

1. **`load_pyrogen` now honours `Cp_gas`.** Because `_pyrogen_from_mapping`
   reads `Cp_gas` (the old `load_pyrogen` ignored it when present). No library
   YAML sets `Cp_gas`, so all library loads are unchanged (verified above); only
   a user-authored YAML containing `Cp_gas` behaves differently (was silently
   ignored).
2. **6c block substitution is text-level, not a whole-file yaml load/dump**:
   `.ric` files contain `!!python/object/apply` / `!!python/tuple` tags that
   `yaml.safe_load` rejects (my first attempt failed on this). I replaced only
   the `igniter:` block of the temp copy with a `yaml.safe_dump` of
   `default_igniter_block('bpnv')`, leaving the rest of the file untouched.
3. Existing tests that load stale committed `.ric` igniter blocks
   (`test_all_repo_motors_have_parseable_igniter`,
   `test_build_chamber_from_motor_file_igniter`) now emit
   `StaleIgniterMaterialWarning` into pytest's warnings summary. Expected;
   they still pass (no `filterwarnings=error` configured).
4. `StaleIgniterMaterialWarning` is importable from `srm_1d.openmotor_adapter`;
   I did not add it to the `srm_1d/__init__.py` export list (not in the spec).
5. Baseline suite ran while I was beginning edits (see "Baseline suite").
